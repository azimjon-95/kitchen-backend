# Clean Kitchen — backend

Express + MongoDB (Mongoose) API: рецепты/техкарты, категории, пользователи (admin/manager/staff), QR-коды, OCR, история версий, импорт черновиков.

## Запуск локально
```bash
cp .env.example .env        # задайте MONGODB_URI, JWT_SECRET, ADMIN_*
npm install
npm run build
npm run seed                # 37 демо-карточек (повторный запуск безопасен)
npm start                   # http://localhost:4000/api/health
```
Разработка с автоперезапуском: `npm run dev`.

## Redis
Необязателен. Если задан `REDIS_URL`: публичные списки `GET /api/recipes` кэшируются на 60 с (заголовок `X-Cache: HIT/MISS`), любое изменение карточек сбрасывает кэш, лимиты запросов хранятся в Redis. Если Redis недоступен — сервер продолжает работать с MongoDB.

## Синхронизация для офлайн-клиентов
`GET /api/sync/recipes` — полный набор опубликованных карточек; `GET /api/sync/recipes?since=<serverTime>` — только изменённые и список `removedIds`. Мобильное приложение хранит всё на устройстве и при появлении интернета запрашивает только новое.

## Всё сразу локально
`docker compose up --build` — MongoDB + Redis + API (нужен `.env`).

## Деплой
**Render:** New → Blueprint → этот репозиторий (`render.yaml`). Задайте `MONGODB_URI` (Atlas), `CLIENT_ORIGIN` (адрес клиента на Vercel), `ADMIN_EMAIL`, `ADMIN_PASSWORD`. `JWT_SECRET` сгенерируется сам. После первого запуска выполните `npm run seed:prod` в Shell (по желанию).

**Docker (любой сервер/Railway/Fly):**
```bash
docker build -t clean-kitchen-api .
docker run -p 4000:4000 --env-file .env clean-kitchen-api
```

**Клиент:** в Vercel добавьте переменную `VITE_API_URL=https://<адрес-api>` (без `/api` на конце — см. README клиента) и пересоберите.

## Основные эндпоинты
`GET /api/health` · `POST /api/auth/login` · `GET /api/recipes?limit=200` (опубликованные — публично) · `POST /api/recipes` · `POST /api/recipes/import-draft` (admin/manager, всегда `draft`) · `GET /api/qr/:id` · `GET /api/categories` · `/api/users`, `/api/ocr`. Подробнее — `docs/API.md`.

## Безопасность
- `.env` в git не хранится; смените `ADMIN_PASSWORD` после первого входа.
- Вход ограничен rate-limit (20 попыток / 15 мин), OCR — 10 запросов в минуту.

## Голосовое распознавание (`/api/voice`)

- `GET /api/voice/status` — включено ли серверное распознавание.
- `POST /api/voice/transcribe?lang=ru` — тело `audio/wav` (16 кГц), ответ `{ text }`. Отсекает тишину и типичные «галлюцинации» Whisper, подсказывает модели названия блюд из базы.
- Включение: в `.env` задать `STT_API_KEY` (по умолчанию Groq, модель `whisper-large-v3`; для OpenAI-совместимых сервисов — `STT_API_URL` и `STT_MODEL`). Лимит 30 запросов в минуту.
- Точность зависит от провайдера; на живой речи с акцентами не проверялась.


## Multi-tenant платформа (RBAC) — `/api/v1`

Один backend и одно клиентское приложение обслуживают много независимых ресторанов.

**Роли**: Super Admin (платформа) → Владелец → Управляющий → Шеф / Су-шеф → Повар → любые пользовательские роли. Владелец сам создаёт роли и настраивает матрицу прав (`view, create, edit, delete, publish, archive, import, export, approve` по каждому разделу), доступ ко всем / выбранным категориям / отдельным картам / цехам, скрытие себестоимости, запрет правки закупочных цен, доступ на ограниченный срок. Нет явного разрешения — запрет.

**Изоляция ресторанов**: каждая ресторанная сущность содержит `restaurantId`. Ресторан определяется только из серверной сессии (никогда из тела, URL или заголовков); при каждом запросе проверяются сессия, пользователь, статус ресторана, членство, окно доступа и право. Модели защищены `tenantGuard`: запрос к ресторанной коллекции без `restaurantId` отклоняется на уровне Mongoose. Чужая карточка по подставленному ID — 404.

**Авторизация**: Argon2id; access-токен 15 мин (в памяти клиента); refresh-токен — opaque, HttpOnly cookie, ротация + обнаружение повторного использования (вся семья отзывается); CSRF: белый список Origin + обязательный заголовок `X-CK-CSRF`; блокировка входа после 5 неудач; смена пароля и блокировка аккаунта мгновенно отзывают сессии; восстановление пароля через одноразовый токен (30 мин).

**Запуск**: задайте `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `APP_ORIGIN`, `SUPER_ADMIN_EMAIL/PASSWORD` (см. `.env.example`). Super Admin создаётся при первом старте (идемпотентно). Дальше: войти → создать ресторан и владельца → владелец создаёт сотрудников и роли.

**Тесты**: `npm test -w @clean-kitchen/server` (нужна MongoDB; `MONGODB_URI_TEST=mongodb://127.0.0.1:27017`) — 42 интеграционных теста: изоляция ресторанов, RBAC, подмена `restaurantId`, privilege escalation, сессии/refresh/CSRF, блокировки, Audit Log.

**Ограничения (честно)**:
- Письма для сброса пароля сервер не отправляет: токен выдаётся владельцем/Super Admin (`/members/:id/reset-password-token`) или логируется; подключите свой почтовый сервис.
- Фото и PDF сейчас не хранятся на сервере (OCR обрабатывает файл в памяти), поэтому изоляции файлов хранить нечего; при добавлении хранилища ключи нужно строить как `<restaurantId>/…`.
- WebSocket в проекте нет. Старый однотенантный API (`/api/recipes`, `/api/sync` — общий демо-каталог) оставлен для демо-режима клиента; в продакшене отключите `LEGACY_API=off`.
- `/api/ocr` и `/api/voice` не привязаны к ресторану (не хранят данных), защищены лимитами запросов.
